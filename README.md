## Цель и входные данные

Программа определяет момент заказа товара у поставщика, рекомендуемый объём заказа, число дней до исчерпания остатка и состояние запаса.

Вводятся: текущий запас `stock` (шт.), дневной спрос `daily_demand` (шт./день), срок поставки `lead_days` (дни), запас безопасности `safety_days` (дни), максимальный объём заказа `max_order` (шт.) и надёжность поставщика `reliability` (%).

Рассчитываются:

- `reorder_point = daily_demand * (lead_days + safety_days)`;
- `expected_during_lead = daily_demand * lead_days`;
- `target_stock = reorder_point + daily_demand * safety_days`;
- `recommended_order = min(max_order, max(0, target_stock - stock))`;
- `days_left = stock / daily_demand` с целочисленным делением.

Статус выбирается с приоритетом сверху вниз: `CRITICAL`, если запас меньше ожидаемого расхода за срок поставки или надёжность ниже 70%; иначе `ORDER_NOW`, если запас не выше точки заказа; иначе `SUPPLIER_WARNING`, если надёжность ниже 85%; иначе `ENOUGH`.

## Текущая декомпозиция

| Функция | Ответственность и контракт | Побочные эффекты |
|---|---|---|
| `max(a, b)` | Возвращает большее из двух целых чисел. | Нет |
| `min(a, b)` | Возвращает меньшее из двух целых чисел. | Нет |
| `is_input_valid(...)` | Возвращает 1, если все целые входы неотрицательны и обычное число `reliability` сравнениями попадает в `[0, 100]`; иначе возвращает 0. Нулевой спрос проверяется отдельной функцией. Значение NaN текущая проверка ошибочно принимает. | Нет |
| `calculating_days_left(daily_demand)` | Возвращает 0 при нулевом спросе и 1 в остальных случаях. Предусловие основного сценария: спрос неотрицателен. | Нет |
| `get_status_code(...)` | Возвращает 1 для `CRITICAL`, 2 для `ORDER_NOW`, 3 для `SUPPLIER_WARNING`, 4 для `ENOUGH`; приоритет соответствует правилам варианта. | Нет |

В `main` находятся ввод/вывод, порядок вызова функций и сами пять формул. Это корректное минимальное число пользовательских функций для базовой части, но ввод через `scanf` сейчас не проверяет количество успешно прочитанных значений. Кроме того, `get_status_code` вызывается повторно для каждой ветви итогового вывода.

## Ограничения входов и найденные риски

Реально реализованная проверка отклоняет отрицательные целые входы и надёжность вне `[0, 100]`. Нулевой спрос отдельно приводит к сообщению `UNPROFITABLE BUSINESS`. Верхние границы для целых параметров не проверяются.

Для ручных расчётов и тестов ниже используется безопасная область: `stock` и `max_order` — от 0 до 1 000 000; `daily_demand` — от 1 до 10 000; `lead_days` и `safety_days` — от 0 до 365; `reliability` — конечное число от 0 до 100. В этой области наибольшее промежуточное значение `target_stock` равно 10 950 000 и помещается в обычный 32-битный `int`. Это пока **описанная тестовая область**, а не гарантируемая ограничениями программы: верхние границы необходимо добавить в `is_input_valid`, если они будут приняты для сдачи.

Также перед сдачей следует проверить возвращаемое значение каждого `scanf`. Сейчас текст вместо числа может оставить переменные неинициализированными; большие числа могут переполнить целочисленные формулы. Проверка через `NaN` подтвердила ещё один дефект: нечисловое значение надёжности принимается и даёт `ORDER_NOW`. Эти случаи не объявлены успешно обработанными текущим кодом и не включены как PASS-тесты.

## Независимые расчёты

**C-01.** При `stock=47`, `daily_demand=8`, `lead_days=4`, `safety_days=3`, `max_order=25`, `reliability=90`:

1. `reorder_point = 8 * (4 + 3) = 56`.
2. `expected_during_lead = 8 * 4 = 32`.
3. `target_stock = 56 + 8 * 3 = 80`.
4. `recommended_order = min(25, max(0, 80 - 47)) = min(25, 33) = 25`.
5. `days_left = 47 / 8 = 5` целых дней.
6. `47 >= 32`, `90 >= 70`, `47 <= 56`, поэтому статус — `ORDER_NOW`.

**D-05.** При `stock=61`, `daily_demand=10`, `lead_days=4`, `safety_days=2`, `max_order=100`, `reliability=85`:

1. `reorder_point = 10 * (4 + 2) = 60`; `expected_during_lead = 40`.
2. `target_stock = 60 + 10 * 2 = 80`.
3. `recommended_order = min(100, max(0, 80 - 61)) = 19`; `days_left = 61 / 10 = 6`.
4. Запас выше 60 и надёжность не ниже 85%, поэтому статус — `ENOUGH`.

## Короткая подготовка к защите

- **Цель:** программа помогает решить, когда заказывать товар, сколько заказать с учётом лимита поставщика и какой статус присвоить текущему запасу.
- **Почему `max` и `min` отдельные:** каждая возвращает одно значение и не зависит от ввода/вывода; их можно проверить отдельно.
- **Почему `calculating_days_left` не делит:** это guard-функция, которая не допускает деление на ноль; само деление остаётся в основном сценарии. Название можно сделать точнее.
- **Почему `CRITICAL` имеет приоритет:** условие варианта проверяется раньше остальных. В D-07 одновременно выполняются критический уровень и условие заказа; правильный результат — `CRITICAL`.
- **Что улучшить:** проверять чтение всех шести значений, отвергать не конечную надёжность и ограничивать числа безопасной областью перед целочисленными вычислениями.
